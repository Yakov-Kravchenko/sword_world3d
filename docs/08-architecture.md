# 08. Техническая архитектура

Целевая версия: **Godot 4.4+**, рендерер **Forward+**, язык **GDScript со статической типизацией** (не C#).

**Почему GDScript, а не C#:** для команды с нулевым опытом критична скорость итерации и объём документации/примеров. C# даёт выигрыш в производительности только на тяжёлых вычислениях; у нас такое одно (ИИ и генерация), и оно решается вынесением в поток и оптимизацией алгоритма. Смешивать языки в первом проекте — гарантированные проблемы со сборкой и экспортом.

**Обязательное правило:** `class_name` + типизация всех переменных, параметров и возвратов. `@warning_ignore` только с комментарием-обоснованием.

## 1. Главный архитектурный принцип

> **Правила игры не знают о движке.**

```
┌─────────────────────────────────────────────────────┐
│  core/   — чистый GDScript: RefCounted и Resource   │
│            без нод, без сцен, без _process           │
│            боевая математика, генерация подземелий,  │
│            инвентарь, лут, экономика, сохранения     │
│            ↑ ПОЛНОСТЬЮ ПОКРЫТ ЮНИТ-ТЕСТАМИ           │
└─────────────────────────────────────────────────────┘
                        ▲
                        │ команды / события
                        ▼
┌─────────────────────────────────────────────────────┐
│  game/   — ноды и сцены: визуализация состояния     │
│            камеры, анимации, VFX, ввод, UI           │
│            НЕ содержит правил, только отображение    │
└─────────────────────────────────────────────────────┘
                        ▲
                        │ читает
                        ▼
┌─────────────────────────────────────────────────────┐
│  data/   — .tres ресурсы: предметы, враги, заклинания│
│            биомы, модули комнат, баланс              │
└─────────────────────────────────────────────────────┘
```

Практическая выгода: боевую систему можно прогнать 10 000 раз в симуляторе за секунды; баг воспроизводится тестом, а не «поиграй 20 минут и посмотри».

## 3. Автозагрузки (синглтоны)

Строго ограниченный список. Всё остальное — обычные объекты.

| Автозагрузка | Ответственность |
|---|---|
| `EventBus` | Глобальные сигналы. Единственный способ связи UI ↔ логика. Никаких `get_node("../../..")` |
| `GameState` | Текущее состояние: профиль, активный забег, отряд, флаги |
| `Database` | Реестр всех `.tres` ресурсов по id. Загружается при старте, отдаёт `get_item("sword_iron")` |
| `Balance` | Загруженный `balance.tres`, доступ к константам |
| `SaveSystem` | Сохранение/загрузка, миграции, автосейв |
| `SceneRouter` | Переходы между сценами с экраном загрузки и фоновой подгрузкой |
| `AudioManager` | Музыка (кроссфейд), SFX-пул, эмбиент, шины |
| `Settings` | Настройки игрока, применение к движку |
| `InputMap2` | Перебиндинг, поддержка геймпада |
| `Log` | Логирование в файл с уровнями, важно для багрепортов из Steam |

**Правило:** автозагрузка не содержит игровых правил, только хранение и маршрутизацию.

### 3.1 EventBus: пример

```gdscript
# game/autoload/event_bus.gd
extends Node

# Бой
signal combat_started(state: CombatState)
signal turn_started(actor_id: StringName)
signal action_resolved(result: ActionResult)
signal damage_dealt(target_id: StringName, amount: int, type: StringName, is_crit: bool)
signal status_applied(target_id: StringName, status: StringName, stacks: int)
signal actor_died(actor_id: StringName)
signal combat_ended(victory: bool)

# Забег
signal floor_loaded(floor_index: int, biome: StringName)
signal torch_state_changed(ticks_left: int)
signal blessing_offered(options: Array[BlessingData])
signal run_ended(summary: RunSummary)

# Инвентарь и мета
signal item_acquired(item: ItemInstance)
signal currency_changed(kind: StringName, amount: int)
signal upgrade_attempted(item: ItemInstance, success: bool)
```

UI подписывается на эти сигналы и никогда не лезет в `core/` напрямую для записи — только читает состояние.

## 4. Данные: подход data-driven

Весь контент — ресурсы Godot (`.tres`). Ни один враг, предмет или заклинание не описывается кодом.

```gdscript
# core/items/weapon_data.gd
class_name WeaponData
extends ItemData

@export var damage_dice: String = "1d8"        # парсится Dice.parse()
@export var damage_type: StringName = &"slashing"
@export_enum("STR", "DEX", "INT", "WIS") var attack_stat: String = "STR"
@export var range_cells: int = 1
@export var properties: Array[StringName] = []  # two_handed, light, finesse, heavy, reach
@export var slot: StringName = &"main_hand"
@export var allowed_affix_pools: Array[StringName] = []
```

**Валидатор контента** (`tools/validate_data.gd`, запускается в CI и по кнопке): проверяет, что все id уникальны, все ссылки разрешаются, у каждого врага есть таблица дропа, у каждого заклинания есть иконка, кости урона парсятся, аффиксы совместимы с категориями. ⚠️ Без этого при 500+ ресурсах опечатки станут основным источником багов.

### 4.1 Расширяемость: содержание релиза задаётся данными

Игра выходит в объёме **Варианта Б** (20 этажей, 2 акта, 6 биомов, уровни 1–9, улучшение до +8) и дорастает до полного объёма пострелизными обновлениями. Чтобы это не потребовало переписывания, ни одно из следующих значений не должно появляться в коде как литерал, длина массива или значение `enum`:

| Значение | Где живёт | Релиз | После обновлений |
|---|---|---|---|
| Число актов и длина акта | `balance.tres` | 2 × 10 | 3 × 10 |
| Этажи боссов, Вестников, благословений, Врат | `balance.tres` (массивы) | [10,20] и т.д. | [10,20,30] |
| Максимальный уровень отряда | `balance.tres` | 9 | 12 |
| Таблица ячеек заклинаний | `balance.tres` (2D-массив) | до 3-го ур. | до 5-го |
| Потолок улучшения | `balance.tres` | 8 | 10 |
| Максимальный тир аффикса | `balance.tres` | 4 | 5 |
| Список биомов и «глубоких» версий | `data/biomes/*.tres` | 6 + 6 | 10 + 10 |
| Тиры руды | `data/items/materials/` | 3 | 4 |
| Ряды дерева навыков | `data/skills/*.tres` | 5 + 4 ствола | 8 + 3 |

**Следствия для кода, которые проверяются на ревью:**
- UI дерева навыков, экран уровней и панель кузницы строятся из данных, а не из фиксированной вёрстки.
- Профиль игрока, сохранённый в релизной версии, обязан открываться в версии с актом III — покрыто тестом миграции.
- Достижения заводятся сразу под полный список; неиспользуемые не публикуются в Steam.
- Заклинания, узлы и биомы, помеченные `available_from_version`, грузятся, но не выдаются игроку.

## 5. Детерминированный RNG

Критично для процедурной генерации, воспроизведения багов и честности.

```gdscript
# core/util/rng_stream.gd
class_name RngStream
extends RefCounted

var _rng := RandomNumberGenerator.new()

func _init(seed_value: int, stream_name: StringName) -> void:
    _rng.seed = hash_combine(seed_value, stream_name)

static func hash_combine(a: int, b: Variant) -> int:
    return hash(str(a) + "|" + str(b))
```

**Отдельные потоки RNG** на каждую подсистему, чтобы изменение одного не сдвигало другое:

| Поток | Сид |
|---|---|
| Генерация этажа | `hash(run_seed, "floor", floor_index)` |
| Состав встреч | `hash(run_seed, "encounter", floor_index, room_index)` |
| Лут | `hash(run_seed, "loot", floor_index, room_index)` |
| Броски боя | `hash(run_seed, "combat", combat_index)` — сохраняется состояние! |
| Ассортимент лавки | `hash(profile_seed, "shop", day)` |

⚠️ **Запрещено** использовать глобальные `randi()` / `randf()` где угодно, кроме визуальных эффектов. Проверяется грепом на ревью.

**Бросок костей боя** сохраняется вместе с забегом (состояние RNG сериализуется) — иначе save-scumming через перезагрузку сломает рогалик.

## 6. Машина состояний боя

```
IDLE → START_COMBAT → ROLL_INITIATIVE → TURN_START
   → (PLAYER_INPUT | AI_THINK) → ACTION_DECLARED → ACTION_VALIDATE
   → ACTION_RESOLVE → ACTION_ANIMATE → REACTIONS → TURN_END
   → (следующий актёр) TURN_START | ROUND_END | COMBAT_END
```

**Ключевой приём:** логика и анимация разделены.
1. `CombatEngine` полностью разрешает действие и возвращает `ActionResult` — структуру со всеми бросками, уроном, эффектами.
2. `CombatView` проигрывает этот результат как анимацию.
3. Состояние игры уже изменилось до начала анимации.

Это даёт: мгновенный симулятор для баланса, возможность ускорения/пропуска анимаций, отсутствие рассинхрона между «что показали» и «что случилось».

```gdscript
# core/combat/action_result.gd
class_name ActionResult
extends RefCounted

var actor_id: StringName
var action_id: StringName
var targets: Array[StringName]
var rolls: Array[RollRecord]        # каждый бросок с формулой для лога
var damage_events: Array[DamageEvent]
var status_events: Array[StatusEvent]
var movement: Array[Vector2i]
var resources_spent: Dictionary
var log_lines: Array[String]
```

## 7. Сохранения

### 7.1 Что сохраняется

**Профиль** (`user://saves/profile_<n>.json`) — мета-прогресс:
```
версия_схемы, id_основного_героя, день
валюты, склад[], дома{декор[], уровни_зданий}
деревья_навыков{}, уровень_отряда, открытые_биомы[], лор[], рецепты[]
статистика, достижения, сид_профиля
```

**Забег** (`user://saves/run_<n>.json`) — активный забег:
```
версия_схемы, run_seed, состояние_rng_потоков
этаж_индекс, биом, план_этажа (компактно: сид + дельта состояний комнат)
отряд[]: HP, ячейки, статусы, инвентарь, экипировка, кости_здоровья
благословения[], таймер_факела, использованные_алтари[]
позиции, открытые двери, разграбленные ящики, обезвреженные ловушки
```

### 7.2 Правила надёжности

- Формат: **JSON** (читаемый, легко чинить руками при поддержке игроков).
- **Атомарная запись:** пишем в `*.tmp` → `FileAccess` закрываем → `DirAccess.rename()`. Никогда не пишем поверх.
- **Резервная копия:** перед перезаписью сохраняем предыдущий как `*.bak`. При повреждении основного грузим `.bak` с уведомлением.
- **Версия схемы** в каждом файле. Миграции — цепочка функций `migrate_v1_to_v2()`. Никогда не ломаем сейвы игроков после релиза.
- **Автосохранение:** при спуске на новый этаж, при каждом отдыхе, при выходе из подземелья, при выходе из игры.
- Сохранение забега = «Сохранить и выйти», один слот. Загрузка **удаляет** файл забега в момент загрузки и пересоздаёт при следующем автосейве — защита от save-scumming через копирование файла средствами игры (полностью защититься нельзя и не нужно).

## 8. Производительность: бюджеты под GTX 1660 / 8 ГБ RAM

### 8.1 Целевые показатели

| Показатель | Цель | Максимум |
|---|---|---|
| FPS в подземелье, 1080p | 60 | не ниже 45 |
| FPS в деревне, 1080p | 60 | не ниже 50 |
| Время генерации этажа | 1.0 с | 1.5 с |
| Время загрузки этажа (с материализацией) | 2.5 с | 4 с |
| RAM всего процесса | 2.5 ГБ | 3.5 ГБ |
| VRAM | 2.0 ГБ | 2.8 ГБ |
| Draw calls | 900 | 1 500 |
| Треугольников в кадре | 350 000 | 600 000 |

### 8.2 Правила рендера

| Правило | Обоснование |
|---|---|
| **Источников света с тенями в кадре: 1–2** | Тени — главный убийца FPS. Факел даёт тени, остальное — без |
| **SDFGI / VoxelGI выключены** | Процедурная геометрия не позволяет запечь, реалтайм GI неподъёмен |
| **SSAO выключен**, вместо него — запечённая AO в текстурах модулей | Дёшево и достаточно для стиля |
| **Плотный туман** (`fog_enabled`, depth fog) | И стиль, и обрезка дальности отрисовки |
| **OccluderInstance3D** на стенах модулей | Ключевая оптимизация подземелья: не рисуем соседние комнаты |
| **MultiMeshInstance3D** для декора, камней, костей, мебели | Сотни объектов за 1 draw call |
| **Без нормал-мап**, материалы без металла кроме оружия | Экономия VRAM и времени художника |
| **Текстурные атласы** на биом (2048×2048) | Батчинг |
| **LOD:** 2 уровня для врагов, 1 для пропсов | Godot 4 умеет автоматически |
| **Тени: shadow atlas 2048**, дальность теней 20 м | Свет всё равно не бьёт дальше |
| **VSync on, лимит 60 FPS** по умолчанию | Стабильность важнее пиков |
| **Пулы объектов** для VFX, снарядов, декалей | Избежать GC-пауз |

### 8.3 Память

- В памяти **только текущий этаж**. Предыдущий выгружается через `queue_free()` + явный `ResourceLoader` unload.
- Загрузка следующего этажа — `ResourceLoader.load_threaded_request()` под экраном загрузки.
- Все ассеты биома пакуются в один набор; при смене биома освобождается предыдущий.
- Иконки и UI-атласы держатся постоянно (небольшие).
- ⚠️ 8 ГБ RAM — это ~5.5 ГБ доступных под Windows 10 с браузером. Держим 2.5 ГБ, регулярно проверяем на минимальной машине. **Тестировать на реальном железе минимальной конфигурации не реже раза в 2 недели.**

### 8.4 Тяжёлые вычисления

- Генерация этажа и оценка ИИ — в `WorkerThreadPool` или отдельном `Thread`. Основной поток не блокируется дольше 16 мс.
- Профилирование: встроенный профайлер Godot + собственные метки `Log.perf()` вокруг генерации, ИИ и загрузки.

## 9. Тестирование

### 9.2 Интеграционные тесты

- Полный автобой: отряд ур. 5 против стандартной встречи глубины 10, 500 прогонов — без исключений, метрики в диапазоне.
- Полный забег в headless: 20 этажей с ИИ-игроком (простая эвристика) — без вылетов.
- Сохранение/загрузка на каждом этаже забега — состояние идентично.

### 9.3 CI

GitHub Actions: на каждый push — `godot --headless --script addons/gut/gut_cmdln.gd -gdir=res://tests -gexit` + `validate_data.gd`. Сборка Windows-экспорта на теги.

**Порядок в файле:** `class_name` → `extends` → docstring → сигналы → enum → константы → `@export` → публичные переменные → приватные → `_ready` и жизненный цикл → публичные методы → приватные методы.

**Git:** ветки `main` (стабильная) / `dev` / `feature/*`. Godot-проект требует **Git LFS** для `assets/` (модели, текстуры, звуки) — настроить с первого дня, иначе репозиторий распухнет. `.gitattributes` с `*.png`, `*.glb`, `*.ogg`, `*.wav` → LFS.

## 12. Риски и технический долг

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| ИИ тормозит при 8 врагах | Высокая | Среднее | Ограничение перебора, кэш путей, поток, ранняя оптимизация в Фазе 1 |
| Генератор выдаёт несвязные этажи | Средняя | Высокое | Проверка связности + fallback-этаж + 1000-сидовый тест в CI |
| Не влезаем в 8 ГБ RAM | Средняя | Высокое | Один этаж в памяти, регулярный замер, тест на реальном железе |
| Сейвы ломаются между версиями | Высокая | Высокое | Версия схемы + миграции с первого дня, тесты round-trip |
| Объём контента не потянуть вдвоём | **Очень высокая** | **Критическое** | Общий риг, `shared`-модули, процедурные элитки вместо уникальных боссов, жёсткий отказ от фич вне ТЗ |
| Перебалансировка вручную съест месяцы | Высокая | Высокое | Симулятор боя в Фазе 1 |
| Обновление Godot ломает проект | Средняя | Среднее | Фиксировать минорную версию, обновляться только между фазами, с прогоном тестов |
